# 0.4.1 maintenance release

- Status: Candidate preparation; not published.
- Authority: the maintainer authorized necessary version, tag, and publication work on
  2026-10-26 for Dependabot PRs #81 and #82.
- Release route: the existing tag-only workflow from [ADR 0006](../decisions/0006-publish-open-vsx-from-version-tags.md).
- API floor: VS Code `^1.123.0`; compile-time VS Code types `1.120.0`; Node tooling `24.18.0`.
- Current editor qualification: VS Code `1.143.1` and VSCodium `1.140.06880`
  (Extension Host API `1.140.0`).

The maintenance changes update development tooling and its security overrides. The
production dependency set and local-only extension boundary are preserved. See the
2026-10-26 amendments in [ADR 0013](../decisions/0013-development-tooling-security-updates.md)
for the MSAL API/reachability review and the real Open VSX CLI loopback test.

Published `v0.4.0` is the explicit upgrade predecessor. Its downloaded universal VSIX
must match its released checksum. Historical performance and lifecycle receipts do
not qualify the new candidate. The release checklist records the remaining gates;
no publication result is claimed until the tagged workflow and public artifacts are verified.

## Single same-environment published-0.4.0 control

The single [0.4.0 control run](evidence/0.4.0-linux-control.md) also fails QR-002:
**1863 ms p95 across 20 samples**, compared with the candidate's 1793 ms. Both
pass QR-003 with `d3` and the headed Webview network observation. Both use VS Code
1.143.1 (commit `e646868227c3e3a9e3f24277c8c7220be42c0be7`), Electron 43.7.7,
Chromium 150.0.7871.250, the same measurement scripts and Playwright 1.64.1,
fixture seed 5196614, Linux/Xorg dummy display at 1920x1080/24-bit, five virtual
CPU threads on AMD EPYC 9V74, 17.59 GiB memory, and Vulkan SwiftShader. The same
recorded sandbox/software-rendering and background-throttling arguments apply.

[Byte-parity evidence](evidence/0.4.0-control-byte-parity.json) verifies all four
measured runtime files against the checksum-verified published 0.4.0 VSIX, both
before and after measurement. Its published Wasm uses the genuine historical
build receipt with matching source-input hash; a fresh Linux compilation differs,
so it is not substituted for the released Wasm. Historical performance results
are not reused: this is a new capture of those exact bytes. The complete
[control raw JSON](evidence/0.4.0-linux-control.json) is retained.

The candidate is 70 ms lower in this one pair, and the published control also
misses the limit substantially. This supports an environment effect and does not
show a regression caused by the dependency remediation. It does not prove absence
of regression: these are single runs, the published release is not the immediate
pre-PR main revision, and production dependencies also changed since 0.4.0.
The isolated control keeps its original esbuild 0.28.1 to reproduce released JS;
the candidate uses reviewed esbuild 0.28.2. Measurement scripts and the CDP client
are shared, while runtime/graph dependencies intentionally remain version-specific.
The [PR #81/#82 payload comparison](evidence/dependabot-runtime-parity.json) separately
confirms byte-identical JS/CSS/Wasm files across those two dependency candidates.

At the end of this Linux comparison, the 0.4.1 performance gate remained failed. A strict-passing, complete measurement
of the final candidate on a suitable environment is required before tagging.
No runtime optimization, threshold relaxation, new environment, credential, tag,
or publication is authorized by this comparison or performed as a workaround.
